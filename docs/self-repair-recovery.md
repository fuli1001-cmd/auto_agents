# Self-repair 的验收、交付与恢复

修复事务保留原始目标、交接关系和调用消耗。代码通过验收只表示可以交付；只有已登记的原任务进程确认进入约定子流程，才表示恢复成功。

## 目标总账与当前故障

恢复协议 2 分别绑定目标、故障、修复合同和运行产物。目标总账跨事务保存消耗；一个事务只处理对应故障，不能仅因交接编号相同而接管后来的另一项失败。旧请求、现场、候选和消费记录不覆盖、不清零。

`FailureIncident` 从实际执行结果提取阶段、检查项、会话和原交接。成功预检不是失败；后来的 `verify` 失败会成为当前故障。返回包装没有直接子引用时，须先核验结果中记录的子流程与原交接归属。相同未解决故障的重复观察继承编号并追加版本；成功恢复后再次发生的故障使用新编号。

原故障的必要性判断，在目标、故障条件、相关源码证据和候选不变时复用。相同故障的新现场单独封存为恢复检查用例；不能拿历史现场替换新观察。候选测试失败、测试修订待审核和验证环境失败各有处理归属，不能直接作为修改引擎的许可。

历史迁移只根据持久化的真实接管确认，将同一已解决故障的旧事务标记为被替代。迁移索引独立保存；其他故障、旧回执和原消费记录保留。界面区分本次实施与历史累计实施。

## 证据来源与测试修订

证据明确来自任务现场或当前引擎，并绑定内容摘要。历史引擎基线只用于回归比较；当前源码引用由当前引擎快照验证。模型与检查器共享相同的现场证据清单。大日志可引用经过摘要核验的具体执行事件，不放宽整文件大小限制。诊断清单额外提供脱敏的当前故障摘要。

修改受保护测试的候选进入独立只读审核。审核不复用实施者会话，检查原目标、关联需求及实际候选差异。新增 unittest 用例和既有预期修订可以审核；删除原测试、修改收集控制、添加跳过机制或危险定义仍由确定性规则拒绝。

通过后产生 `ProofAmendmentReceipt`，仅对该候选、原绑定和精确文件修订生效。原证明、写入凭据和任务归属保持不变。验证身份包含审核凭据，修订涉及的测试加入强制执行；审核结论本身不是测试通过证明。

审核还须说明每个实际改动路径与原目标的关系。获批测试在选择验证范围前作为临时步骤加入，其明确覆盖的改动不再触发“未映射改动”的全项目回退。未覆盖的路径仍按原回退策略处理；显式全量验证和配置中的发布阻塞路径仍然生效。修订测试必须提供实际通过的节点记录，只有收集结果、跳过或进程退出成功不能交付。

审核拒绝时反馈给原候选修正流程；服务不可用、格式错误和未知调用结果暂停原流程，保留候选。已持久化的审核回复可在重启后继续处理；已通过的相同审核不重复调用。审核消耗记入目标模型调用总账，不增加产品实施次数。

目标变化或需求含义不明时，复用终端交互选择。`--auto-approve` 不代替用户选择；决定和候选可跨退出、重启保留。继续时优先审核及验证原候选，不重新实施，也不重新启动旧引擎计划。

## 运行产物

`RuntimeArtifact` 使用独立 Git 仓库，包含自己的对象和元数据，不依赖工作树的外部 `gitdir`、`commondir` 或 `alternates`。源码提交、文件内容、格式和环境引用共同决定产物身份。路径可以迁移，身份必须保持一致。

控制器先生成产物并在隔离容器检查独立启动，再执行原阻塞预检、测试、审查和行为对照。交付直接使用这份产物，不能在验收后换成另一种目录结构。可写测试使用它的临时副本。运行产物保留在事务的恢复证据目录内，沿用现有存储空间检查和证据保留规则。

控制器由 `implementation_root` 单独固定；更新控制器不会自动合入候选。更新已安装引擎源码时，仍须对新候选核验受影响的验收证据。

## 状态与失败归属

事务检查点是修复阶段的权威记录，阶段更新检查修订号。进程数据库负责登记、锁、进程代际和界面投影。恢复操作绑定原目标上下文、运行产物、订阅者和代际。真实确认持久化后，即使进程在更新数据库之前退出，下次控制器轮询也能恢复完成状态。

| 失败 | 恢复位置 |
| --- | --- |
| 源码身份匹配，真实执行证明原子流程仍失败 | 同一候选实施；撤销受影响的组合验收回执 |
| 打包或实际加载身份不匹配 | 运行产物检查；保留代码证据 |
| 已确认的环境或验证设施问题 | 环境准备、重新验证；不调用模型改代码 |
| 控制器、协议或未知问题 | 保留现场并暂停；不默认回到实施 |
| 目标范围需要变化 | 终端交互选择，自动批准参数不代替范围授权 |

新发现必须属于原目标的必要阻塞；无关问题直接跳过，不建立维护待办。必要性证据沿用已有范围协议，实际代码差异仍须逐项审查。

未知结果的模型调用不会在重启后自动重复派发。已确认中断的调用可以续接，历史消耗保留。调用预留以事务和调用编号去重；原有基于已验证进展的停滞检测继续生效，没有新增默认累计调用次数上限。

## 证据复用与旧事务

`PhaseProof` 的复用依据是输入依赖，而非“上次成功”标志。运行产物检查绑定产物身份；恢复检查绑定源码、提交、验证器、现场、原任务上下文和环境快照。已有测试依赖缓存继续使用。输入变化只使受影响的检查失效。

交付检查固定使用验收时的镜像。验证器升级或镜像不可用时，保留代码结果并回到补验；同一源码和控制器不会因环境持续变化反复自动补验。实际接管成功后才开启下一段恢复，调用消耗始终保留。

接管时点的绑定与实施准备后的绑定分别记录。历史失败日志保留；当前是否通过预检依据实际执行的绑定检查判断。接管确认失败会暂停同一交接，父流程不再继续调用模型。

接管边界区分首次实施和保留候选验证。后者必须给出匹配的候选指纹与真实验证身份，不能用到达模型调用位置代替验证。验证步骤选择仅在一次只读计算内共享依赖解析；显式影响路径命中后不再重复解析依赖，下一次选择会重新读取输入。

聚焦修复的验证清单升级到版本 7：显式测试命令已经承担的具体检查，不再因为全项目测试组也能覆盖它，就继承该组的全部未来任务依赖。明确绑定的证明及其前置检查继续保留；已有回归保留，只投影掉有历史源码与任务归属证据证明尚未实现、且未被当前目标接管的检查。迁移通过原有候选绑定桥保存旧清单，不修改原任务授权或产品候选。普通旧清单仍按兼容规则复用。

回归比较固定原始基线，不能通过刷新候选把本轮引入的失败变成历史失败。关键运行、范围归属、预算和恢复测试必须通过，不能通过基线豁免。原始失败报告始终保留。

迁移仅在能证明旧交付失败来自不可独立访问的 Git 元数据时，继承可用的代码阶段证据并重新进入验证。旧回执的撤销记录保留，重新验收产生新的组合回执；历史打包错误不会继续充当候选代码反例。无法证明归属或完整性的记录会停止迁移。

旧版本曾在恢复时清零会话计数。预算迁移先检查原始权威字段和历史前缀；无论计数是否减少，都必须检查预算上限与原记录一致、epoch 没有回退。所有关联会话检查通过后才写入迁移结果。只有新增记录可证明全是控制流程重启、且没有新模型执行时，才恢复已知消耗下限。解释不清的变化会暂停；不推定用户获得了新额度。隔离回放和真实启动使用相同迁移规则。

## 验证

常规回归入口包括 `test_repair_recovery_contract.py`、`test_repair_v2_delivery.py` 和 `test_repair_chain.py`。测试覆盖独立 Git 产物、篡改、证据依赖、错误分流、预算迁移、旧撤销记录和真实 Unix socket/锁传递/进程确认。恢复派发还须运行 `test_parent_recovery_budget.py`、`test_multilayer_engine_recovery.py` 和 `test_reference_catalog_recovery.py`：成功进入实施时只预留一次调用，预检失败时预留零次，父会话预算保持不变。这些测试失败不能作为历史失败豁免。

独立 Docker 验收入口是 `tests/acceptance_repair_runtime.py`，它不包含在容器内部的常规测试收集中，避免递归启动 Docker。使用明确配置的本地镜像和只读现场：

```bash
AUTO_AGENTS_TEST_VERIFIER_IMAGE=<已准备的镜像> \
AUTO_AGENTS_TEST_REPAIR_TRANSACTION=<事务目录> \
AUTO_AGENTS_TEST_PROJECT=<项目目录> \
python -m pytest -v tests/acceptance_repair_runtime.py
```

这个入口复制现场，使用最终运行产物进入原子流程，只截停外部模型调用。真实的实施准备和预算计数仍执行；隔离副本预留一次调用，真实项目不消耗额度。检查父子会话、原交接、真实预检、预算继承及输入未改变。

另外通过完整的控制器验收、验证工作进程和实际恢复启动器，启动一个私有测试项目。登记、锁传递、接管确认和调用计数均使用真实实现；模型服务由本地测试端点代替。覆盖正常账目、旧版清零账目和失败子流程；完整循环还须完成候选写入、测试修订审核、真实测试执行、交付并返回父流程。持有有效回执但预算上限变化或 epoch 回退的场景，隔离回放和实际启动器均须在调用模型前拒绝，且会话记录保持原样。

当前 SDGP 保留候选的专项检查使用其原始逻辑路径，在 Docker 中挂载私有副本及封存依赖。仅在副本内重新登记复制目录的设备、inode；原合同、候选指纹和预算不改写。审核端点由测试替身提供结论，测试执行和交付使用实际实现；不调用真实内容生成供应商。

恢复验收不代表 SDGP 的真实视频目标已完成。该目标仍须由恢复后的 collab 执行并验收。发布沿用原授权策略；远端分叉仅暂停发布，不会在原任务恢复之后再次启动代码修复。
