# Self-repair 收敛调度实现与验证

本次将原方案中的调度、工作项、评审证据、验证版本和上下文优化落实到执行路径。
方案选择以消除实际关键路径上的重复工作为依据，不以迁移或重写成本限制改造。
已有隔离执行器和验证账本继续承担其已验证的职责；收敛决策与证据身份已经改造。

| 改进 | 实际行为 | 质量约束 |
| --- | --- | --- |
| 稳定工作项 | schema 8 的 `work_items` 保存工作身份、定义版本、评审、完成收据和诊断历史。修改文件范围不再丢失证据；唯一可确认的名称变化保留身份 | 重叠组件不能互相借用批准；旧记录须验证归属和摘要 |
| 统一动作路由 | 同时处理真实命令失败和独立代码审查。已有方案覆盖的实现错误直接修正，范围或机制变化进入方案修订，反复出现的反例进入诊断 | 路由不会批准方案、签发测试成功或解除原合同义务 |
| 一次获取必要证据 | 代码审查可同时提供有依据的 `required` 判断、场景映射及负向/正向控制，避免再次询问同一判断 | 排除、延期和不确定的范围仍走单独的独立检查；代码审查不能自行豁免已知问题 |
| 保留方案和反例 | 有效的中断草案可在新环境中直接重新审查。已批准的完整测试文件命令可以作为场景验收，快速检查选择其中明确的节点 | 新增语义问题不进入格式纠正循环；完整回复与增量回复都不能删除旧场景；命令选项和原始调用批次保留 |
| 明确写入优先级 | 当前失败及独立审查的写入要求覆盖旧 `verify_existing` 模式。恢复到以前通过的实现时，允许一次有依据的完整重新验证 | 重新验证不计为新增代码进展，也不能反复续发同样的重试 |
| 反例驱动诊断 | 同一反例跨不同源码修正仍出现时，保留已否定的假设并要求新的区分性检查。相同源码的重复审查不计为新的修复尝试 | 诊断、恢复次数持久化；重复已否定假设不能授权下一次写入，耗尽不等于完成 |
| 固定验证控制面 | 能力观察来自运行中的控制器版本，按版本、实现摘要、环境和代次绑定；候选代码改动不会重新启动外层验证器能力探测 | 候选兼容性仍由实际验收证明；切换版本继续需要外部控制器的固定检查及最终引擎验证 |
| 结构化回复与小型工作输入 | Codex 的范围、方案审查、代码审查及诊断请求使用原生 JSON Schema。实现与复查主要读取当前缺陷和差异，完整历史保存在可追溯引用中 | Schema 只限制格式，语义仍由控制器检查；所有场景的触发条件、预期结果和完整验收仍可检查 |

这些路径没有降低模型或推理配置，没有删除测试、修改缓存失效规则、放宽 sandbox 权限，
也没有把“缺少证据”转换成通过。最终集成、完整测试和原流程恢复的要求保留。

实跑中新增的测试也纳入了保留规则：只有属于原始验收文件、已经独立审查并完成组件验收，
且之后没有再发生未审查修改的测试增量，才能作为后续方案复用的已验证基线。
这不会扩大原方案的写入路径；其他范围外的变化仍需审查。
