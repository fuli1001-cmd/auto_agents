# 自动采用最新源码与即时回收运行快照

状态：已实现；源码、行为测试和安装迁移一并交付。

## 目标与默认语义

用户继续执行原来的 `auto-agents collab/run/fix/resume/verify ...`。启动器负责发现源码变化、生成快照、验证、切换和继续原命令；日常使用不需要显式执行 `repair upgrade`。

“最新代码”采用已确认的默认值：安装绑定的源码目录在本次启动时的稳定内容，包括已跟踪文件的修改、删除，以及未被忽略的新文件。无需用户先提交 Git。

“即时清理”定义为：快照最后一个有效用途消失时立即进入删除流程，无额外保留天数；正常退出同步触发，异常退出由控制进程检测后触发。删除失败有持久重试记录，不把“已安排删除”报告成“已释放空间”。

新版本验证失败时，原命令明确报告启动失败及修复位置；不能静默运行旧版本并声称采用了最新代码。已经启动的命令继续使用它绑定的版本。

## 改造前的问题

- `bootstrap.select_runtime()` 只选择已启用的 `active_runtime`，没有比较工作目录源码。
- `recovery.release.prepare_runtime()` 要求源码已经提交且工作区干净。
- `repair_v2.runtime_artifact.build()` 按提交、源码和环境生成独立 Git 快照。
- `recovery.upgrade.activate()` 更新当前版本、前一版本和运行代次，但不会回收旧目录。
- `recovery.engine.submit()` 已能在自修复完成后调用升级；普通用户命令没有同等入口。
- 旧 console script 仍可能直接导入 `cli.main`，而 `cli.py` 在选择运行版本之前已导入大量业务模块。
- 当前清理器没有接管 `kernel-releases/runtime-artifacts`，也没有解析内核运行版本引用。
- supervisor 的实现选择还依赖源码 `HEAD`，需要与新的内容版本选择统一，否则未提交修改只在前台生效。

## 一、启动时自动同步

### 统一入口

增加安装级 `ensure_current_runtime()`，放在业务参数处理、项目锁、业务状态写入和模型调用之前。

```text
原命令
  → 从安装绑定取得源码目录
  → 捕获源码内容身份
  → 与当前运行版本比较
      相同 → 原子取得使用租约 → 启动原命令
      不同 → 生成不可变快照 → 独立验证
           → 等待已有命令到达可切换状态
           → 回放当前业务历史 → 原子切换
           → 取得新版本租约 → 启动原命令
  → 命令结束释放租约 → 回收失去用途的快照
```

- 源码位置来自安装绑定的 `source_root`，不根据当前目录、SDGP 路径或临时修复目录猜测。
- 普通用户执行入口统一检查；`help/status/stop/cancel` 等诊断和停止入口保持可用，不因新源码验证失败而无法操作。
- 内部子进程、验证容器和恢复续接继承明确的运行版本及租约，不再次追踪工作目录，避免递归升级或版本来回切换。
- 保留 `repair upgrade` 作为兼容的维护入口，它与自动入口调用同一实现。
- 新启动器使用标准库薄层。兼容旧 console script，并将业务 CLI 延迟导入；首次安装新机制时由交付流程更新已有入口，不能只修改 `pyproject.toml`。

### 源码捕获与身份

复用现有 `inventory()/overlay()/freeze()` 的能力，增加供安装级运行时使用的捕获接口。

1. 读取文件清单、文件内容、可执行位和符号链接目标，计算内容摘要。
2. 在私有目录物化同一份内容；处理新增、修改和删除。
3. 再次核对原目录和物化结果。若捕获期间源码变化，重试有限次数；持续变化则明确提示源码正在修改。
4. 在私有仓库中生成所需的提交，保持快照 Git 自包含。原工作目录的分支、索引和提交历史不受影响。
5. 快照身份由内容清单及格式版本决定；来源提交、dirty 标记属于出处信息。相同内容即使后来正式提交，也不重复构建或验证。

沿用 Git 忽略规则排除缓存、运行状态和临时文件；额外明确凭据与本地环境文件的排除规则。新增源码和测试文件进入清单。子模块和指向目录外的链接必须有显式物化支持，否则返回具体路径错误。

源码集合默认采用当前完整交付清单，避免漏掉模板、schema、测试和运行时读取的文档。只改变提交信息、不改变文件内容，不产生新版本。后续若细分运行文件与文档，必须有完整依赖依据。

内容身份与来源身份分离。实现复用兼容的 v1 产物格式：私有提交使用固定作者、时间和基于内容摘要的消息，无父提交，因此相同内容生成相同身份；原源码目录、原 HEAD 和 dirty 状态另存为出处记录。原有 v1 快照同样可复用，不原地改写旧清单。安装内的新运行产物统一存放，历史同内容多副本按准确目录分别登记。

### 验证与启动开销

- 内容未变化：复用已启用版本，不执行升级门禁；仍检查产物完整性并取得租约。
- 新内容：保留现有独立发布门禁，不把自动升级变成跳过验证。
- 静态验证缓存绑定源码摘要、验证器身份、测试清单、依赖锁、解释器/验证镜像及协议版本；任一变化都失效。
- 每次实际切换前都在锁定的业务状态上重新回放当前事件历史。旧静态验证结果不能替代这一步。
- 相同源码、验证器和环境的确定性失败保留诊断结果，避免反复运行昂贵检查；环境变化或显式重试可重新检查，瞬态环境故障不永久缓存。
- 新源码至少需要一次真实验证，因此首次运行可能等待数分钟；后续无变化启动只承担内容检查和租约开销。界面显示当前阶段和待采用版本。

### 切换、并发与自修复

使用三层职责清晰的协调机制：安装级升级锁串行化候选采用；短事务保护运行版本登记和引用；已有项目锁保护业务状态。规定统一锁顺序，验证期间不长期持有业务锁或数据库事务。

- 同一源码的并发启动共享一次构建和验证。等待者在真正启动前重新核对源码，合并到新的目标内容；被替代候选失去引用后立即回收。
- 等待期间只暂停接纳新的外部业务命令。已有命令和其内部子调用可以正常完成，不能提前设置 `draining` 阻止它们推进而造成死锁。
- 等已有业务租约释放或自修复主动交接到可恢复检查点，再取得项目锁、设置短暂切换状态、核对未决副作用、回放日志并更新运行指针和代次。
- 新命令等待切换并显示等待原因，可取消等待；不能为了快速启动而静默降级到旧代码，也不强制终止正在运行的业务。
- 结果不明的模型调用继续遵守已有对账规则。不得以升级为由重发请求、重置预算或重开已解决事件。
- 自修复生成的候选进入同一采用服务。恢复启动使用采用事务签发的一次性续接凭据，避免被源码目录中的旧内容立即覆盖。候选交付回源码目录遵循已有合并与交付协议；并发用户改动需要重新核对，不能强行覆盖。
- supervisor 和 worker 按已验证的产物身份选择实现，不再单独依据源码 `HEAD` 更新。切换前确认协议兼容并在空闲边界更换控制进程。
- 独立基础验证器继续单独绑定，保持固定的既有门禁。已验收的安装管理层提供额外的运行生命周期检查，使用其已有测试验证下一版本；这些扩展检查随管理层自动更新，候选不能自行缩减自己的必需检查。改变基础验证策略本身仍须有独立兼容证据，不能通过普通源码更新暗中放宽检查。

## 二、以引用和租约决定快照寿命

### 唯一登记与保留依据

在控制数据库增加运行产物、引用/租约以及采用事务记录，作为运行快照清理的唯一判定来源。通用 `storage clean` 委托该服务，不建立第二套独立删除判断。

| 记录 | 最小必要信息 |
|---|---|
| 运行产物 | 身份、清单、所属安装、准确路径/目录身份、格式、状态、大小 |
| 持久引用 | 产物、引用类型、所属任务或安装、获取与释放事件 |
| 进程租约 | 产物、进程身份、内核锁/租约句柄、所属操作、子进程继承关系 |
| 采用事务 | 目标内容、原版本、阶段、验证收据、启动请求、恢复信息 |

保留条件是至少存在一个有效用途：

| 用途 | 释放时机 |
|---|---|
| 当前运行版本 | 被新版本成功替换后，转换为回滚用途或释放 |
| 最近一个可兼容回滚版本 | 下次成功升级替换此角色；没有兼容回滚价值时也释放 |
| 当前独立验证器 | 新验证器成功接任且所有验证租约结束 |
| 正在运行的前台、后台、子进程或容器 | 最后一个实际使用者退出 |
| 正在构建、验证或切换的候选 | 采用完成、确定失败或被新请求替代 |
| 未完成任务恢复确实需要的产物 | 交付/恢复完成、引用转移或明确终止其恢复用途 |

同一产物可以承担多个角色。任务处于 paused/blocked 或仅被 cancelled，不自动等于其恢复产物可删；从未决续接、候选交付和引用关系判断。任务虽然 completed，但仍有发布或续接消费者时也不能提前释放。

历史日志或升级收据仅提到产物 ID，不形成永久保留引用。保留精简清单、校验值、验证结论和删除记录；需要实际源码重放的历史任务必须显式登记恢复引用。

### 即时清理时机

在成功切换、验证失败、候选被替代、任务完成、续接消费完成、租约释放和进程退出时，立即计算受影响产物的用途。

- 无持久引用、无活跃进程/容器使用、无进行中的构建或采用事务：当次事件立即回收。
- 不设置“再保留 7 天/30 天”，不保留无用途的“最近 N 个”。一个回滚版本由明确角色保护，不是任意历史数量配额。
- `SIGKILL` 等异常退出由安装控制进程监听并回收失效租约；启动时和 `storage clean` 同样执行补偿扫描。
- “即时”承诺的是最后用途释放时触发回收，不承诺系统关机、文件系统故障或删除权限异常时仍能完成物理删除。待删状态、重试原因和实际释放字节必须可查询。
- 控制进程临时不可用时，正常退出的启动包装器执行清理；需要常驻的后台消费者退出时由其监管者执行相同服务。

### 防止使用与删除竞争

取得版本使用权必须与 GC 使用同一登记事务：先登记引用/租约，再导入代码、启动子进程或挂载容器。所有消费者接入，包括验证器、supervisor、worker、自修复、恢复和维护命令。

```text
ready
  → 无有效用途且重新核对成功
  → deleting（禁止新增租约）
  → 原子移入本安装专用待删目录
  → 释放数据库事务后删除文件
  → deleted（保留小型删除收据）
```

物理删除前核对清单、归属、准确路径、目录 inode 和链接边界；目录身份不同则停止并报告。通用存储的手工 pin、引用和租约也参与保护，清理与这些引用的获取共用存储锁。待合并源码的保留回执同样是有效用途。进程身份包含 boot ID 与启动时刻，不能仅凭 PID 或心跳过期判断进程死亡。容器挂载某个快照的祖先目录时，也会保护其中的快照。

删除中进程崩溃、部分文件已删除、目录已移动等情况均由持久删除记录恢复。新消费者遇到 deleting/deleted 产物只能等待同一内容重新物化，不能引用残缺目录。

清理由当前安装管理器统一执行；仍在退出的旧业务进程将清理请求转交给它，避免继续使用旧清理规则。管理器通常与当前运行版本共用同一产物；业务回退到更早版本时，管理入口仍可保留。限时补偿扫描保存遍历位置，避免前面的保留项耗尽扫描时间、导致后面的垃圾永远无法回收。

正常启动采用带租约的子进程包装，以便业务进程退出后仍有人执行回收；保留退出码、信号和终端交互行为。子进程若晚于父进程退出，租约必须随其真实生命周期保留。内部 `exec` 路径需要显式转移租约。

## 三、旧安装迁移

首次采用本方案由实现交付流程自动完成，引入兼容元数据和新启动入口；用户仍运行原命令。

1. 读取当前、前一版本、验证器、supervisor、未完成修复/续接和进程/容器记录。
2. 校验现有 `runtime-artifacts/*/manifest.json`，把可证明归属的旧产物登记到新系统。
3. 为仍有用途的旧版本建立角色和引用；旧进程没有新租约时，用实际进程/容器观察临时保护，待退出后释放。
4. 在迁移记录提交、引用核对完成且新管理器可工作后，立即清理已确认无用途的旧目录。
5. 损坏或无法判定归属的目录明确报告保留原因，不把“未登记”直接解释为“可删”。后续扫描在信息完整后继续处理。

现有 5 个安装级运行快照是迁移验收样本。不能预先仅根据三个运行指针断定其他两个可删，需要检查任务和进程引用。

运行快照的覆盖范围包括 `kernel-releases/runtime-artifacts`、引擎修复产生的运行产物、controller/worker 使用的独立引擎副本，以及新采用服务产生的临时物化目录。迁移时按既有清单、Git 归属和消费者记录证明每个旧目录的用途，不能仅凭 `runtimes` 目录名认领或删除。

既有修复工作区中的候选快照继续遵守其候选/证据规则；被运行时消费者引用时纳入同一使用登记。可由已封存提交确定性重建、且没有活跃消费者的展开目录可以即时回收；恢复仍必需的提交或唯一内容不能一起删除。不能把产品工作区、媒体、数据库或全部历史证据归入运行快照删除范围。

## 四、代码落点与实施顺序

| 范围 | 改动 |
|---|---|
| `runtime_entry.py`、`bootstrap.py`、`cli.py`、`cli_impl.py` | 标准库前置转交、已安装管理器校验、自动发现变化、租约包装、延迟导入、旧入口兼容 |
| 新 `recovery/runtime_manager.py` | 统一源码选择、验证缓存、并发采用和原命令续接 |
| `repair_v2/runtime_artifact.py`、`workspace.py` | 未提交内容捕获、内容身份、自包含快照和旧格式兼容 |
| `recovery/store.py`、新运行产物生命周期模块 | 产物、用途、租约、删除日志及崩溃恢复 |
| `recovery/release.py`、`upgrade.py` | 分离静态验证与动态历史回放；同一自动/手动采用事务 |
| `recovery/engine.py`、`repair_control.py`、进程/容器启动点 | 自动续接、内容版本一致性、引用和租约覆盖 |
| `artifact_cleanup.py`、`artifact_runtime.py` | 委托运行快照回收；即时触发和维护补偿 |

`runtime_probes.py` 在无网络的只读容器中执行已安装版本的生命周期测试；`runtime_delivery.py` 以可恢复交付记录同步自修复产生的引擎改动。正常前台结束同步回收，控制进程以进程退出观察和补偿扫描处理异常退出；清理结果可由 `repair status --json` 和 `storage clean` 查询。

实施顺序：先补产物登记、租约和恢复机制，再实现内容捕获与自动采用，随后接通事件驱动回收，最后迁移已有安装并验证原命令。先完成消费者引用覆盖，才允许删除旧目录。

## 五、验收标准

1. 仅修改一个引擎文件后直接执行原 `collab` 命令，自动采用对应源码，包含未提交修改。
2. 新增、删除、重命名文件和可执行位变化均得到正确快照；工作目录及 Git 索引不被修改。
3. 同样内容再次执行、或 dirty 内容后来提交，不重复构建和静态验证。
4. 源码捕获或验证期间继续改代码，不会将混合内容或已过时的候选交给原命令。
5. 两个并发启动只执行一次相同内容的采用；内部子进程不会递归升级；等待切换不阻断已有命令完成。
6. 验证失败、磁盘不足或未决副作用时给出准确结果，没有静默使用旧版本、重复付费调用或重置业务预算。
7. 连续多次升级后，目录数量只随有效用途增长。旧回滚角色被替换且租约释放后，其目录在当次流程中删除。
8. 运行中的旧进程、后台子进程、容器、验证器和待恢复任务引用的快照始终可用；最后用途释放后立即回收。
9. 在构建、验证、切换、租约交接和物理删除的各阶段强制终止进程，重启后可以确定性恢复；无丢失运行版本、重复续接或永久待删目录。
10. 旧 5 个快照的迁移报告逐个给出保留/删除依据，删除日志与实际目录、释放空间一致。
11. 旧 console launcher、源码启动器、自修复续接、supervisor 和 worker 实际导入模块的内容身份一致。
